## 1. Purpose

This Data Retention and Deletion Policy (the **"Policy"**) describes how information processed by the Next Step Studios Discord bot (the **"Bot"**) is intended to be retained, reviewed, corrected, archived, and deleted.

It supplements the Bot's Privacy Policy and establishes a framework for preventing unnecessary or accidental long-term retention.

The Bot is operated by **Candler Shaw**, using the public-facing name **Next Step Studios** (the **"Operator"**).

The Bot is intended exclusively for one private Next Step Studios Discord server (the **"Server"**).

This Policy applies to Bot-related information, including information submitted by Users, information generated by Bot Features, and relevant operational records.

It does not govern Discord's independent data retention practices or unrelated services.

## 2. Core Retention Principles

### 2.1 Retain only what is reasonably necessary

Bot Data should be retained only for as long as reasonably necessary for the purpose for which it was collected, subject to applicable law and legitimate operational requirements.

The fact that information is technically easy to store does not, by itself, justify retaining it indefinitely.

### 2.2 Retention must be purpose-specific

Different categories of information serve different purposes and should not automatically share the same retention period.

For example, an unpublished announcement draft does not necessarily need to be retained for as long as an application record or a record of a significant moderation action.

### 2.3 Avoid accidental permanent records

Temporary files, drafts, intermediate workflow data, and diagnostic information should not become permanent records merely because a cleanup process was never implemented.

Each Feature should have a defined lifecycle.

### 2.4 Deletion must be practical

A retention policy is not complete merely because it says information should be deleted.

The Operator must implement and verify a process that can locate and remove the relevant information from active storage and address copies held in backups or other storage locations.

### 2.5 Do not promise unverified deletion timelines

Specific retention periods have not yet been finalized for every category of Bot Data.

Until a schedule is approved and implemented, this Policy does not promise deletion after a particular number of days, weeks, or months.

The Operator must not advertise a fixed deletion deadline that the actual system cannot reliably meet.

## 5. Temporary Files and Drafts

Temporary workflow information should have a defined purpose and lifecycle.

### 5.1 Temporary announcement drafts

Announcement drafts may be stored temporarily while an announcement is prepared, reviewed, or awaiting publication.

The intended lifecycle should address:

- Draft creation.
    
- Draft editing.
    
- Approval or rejection.
    
- Successful publication.
    
- Cancellation.
    
- Expiration.
    
- Recovery following an error.
    

A draft should not remain indefinitely after its purpose has ended unless there is a documented reason to retain it.

### 5.2 Temporary JSON files

Where JSON files are used for temporary workflow state, the Operator should document:

- Which Feature creates the file.
    
- What information it contains.
    
- Whether the file includes personal information.
    
- When it is no longer needed.
    
- What event triggers cleanup.
    
- What happens if cleanup fails.
    
- Whether the file is included in backups.
    

Temporary JSON storage should not be treated as harmless merely because it is not a database.

### 5.3 Cleanup failures

If a cleanup operation fails, the Bot should report or log the failure in a way that does not expose unnecessary User information.

The Operator should investigate the failure and remove the data when it is safe and appropriate to do so.

Repeated cleanup failures should be treated as an implementation issue, not as an acceptable permanent retention method.

## 6. Applications and Staff Records

Application answers and staff-related information are currently understood to be stored in a local database during testing.

The Operator must establish separate retention rules for different application states where appropriate.

### 6.1 Pending applications

Pending applications may need to remain available while they are awaiting review.

They should not be retained indefinitely after the review process has ended without a documented reason.

### 6.2 Approved applications

Approved applications may contain information relevant to an ongoing staff role or administrative responsibility.

The Operator should determine which information remains necessary after approval and avoid retaining unrelated application details simply because they were originally submitted.

### 6.3 Declined applications

Declined applications should have a defined retention period based on legitimate review, administrative, and recordkeeping needs.

The Operator should consider whether the complete original submission is still necessary after the decision has been made.

### 6.4 Withdrawn applications

Where a User withdraws an application, the Operator should review whether the submission can be deleted or whether a limited record is still needed to document the withdrawal or prevent duplicate processing.

### 6.5 Staff records

Information associated with an active staff role may need to remain available while that role continues.

When the role ends, the Operator should review the information and retain only what remains necessary for legitimate administrative, security, or legal purposes.

### 6.6 Retention schedule required

The Operator must establish and document actual retention periods for pending, approved, declined, and withdrawn applications, as well as staff records.

No specific period is promised by this draft.

## 7. Tickets and Support Records

The ticket Feature exists, but the actual transcript-generation and persistence behavior has not been fully verified.

Before production, the Operator must determine exactly what happens to ticket information.

### 7.1 Open tickets

Information in an open ticket may need to remain available while the request is being handled.

Access should be limited to the Operator and authorized individuals responsible for the ticket.

### 7.2 Closed tickets

Closing a ticket should trigger a defined review of what information needs to remain available and for how long.

Closing a ticket should not automatically be treated as permanent deletion unless the implementation actually deletes the relevant information.

### 7.3 Transcripts

The Operator must verify:

- Whether transcripts are generated automatically.
    
- Whether a transcript is sent to a Discord channel.
    
- Whether a transcript is saved to local storage.
    
- Whether the transcript is stored in a database.
    
- Whether multiple copies are created.
    
- Whether attachments are included.
    
- Who can access the transcript.
    
- How each copy can be deleted.
    

A transcript sent to a Discord channel may be subject to Discord's platform behavior and the access permissions of that channel. Deleting a local copy does not necessarily delete a Discord message containing the transcript.

### 7.4 Ticket deletion

The Operator should establish a process for handling deletion requests involving ticket content, transcripts, attachments, and related metadata.

The process must account for each location where a copy may exist.

### 7.5 Retention schedule required

A defined schedule must be established for open tickets, closed tickets, transcripts, attachments, and related records before the ticket workflow is treated as fully documented for production.

## 8. Suggestions and Announcement Records

### 8.1 Suggestions

Suggestion records may be needed to track submissions, review outcomes, and administrative history.

The Operator should define retention rules for:

- Pending suggestions.
    
- Accepted suggestions.
    
- Declined suggestions.
    
- Withdrawn suggestions.
    
- Closed suggestions.
    
- Suggestions removed through an authorized cleanup process.
    

Where a suggestion is publicly published, the Operator should distinguish between the original submission record and the published Discord message.

Deleting one does not necessarily delete the other.

### 8.2 Announcement drafts

Announcement drafts should be treated as temporary workflow information unless a legitimate reason requires retention.

The Operator should define what happens to:

- Unpublished drafts.
    
- Cancelled drafts.
    
- Rejected drafts.
    
- Successfully published drafts.
    
- Failed publication attempts.
    

### 8.3 Announcement history

Announcement history is intended to be stored in SQLite.

The Operator should retain only the information reasonably needed to understand what was published, when it was published, and the relevant administrative context.

The exact fields and retention schedule must be verified.

## 9. Moderation and Infraction Records

Persistent moderation and infraction recordkeeping are planned.

Before implementation, the Operator must establish a retention framework that takes account of the nature of each record.

Potential categories may include:

- Warnings.
    
- Timeouts.
    
- Kicks.
    
- Temporary bans.
    
- Permanent bans.
    
- Removed content.
    
- Related evidence.
    
- Moderator notes.
    
- Corrections or review outcomes.
    

The Operator should not automatically apply one retention period to every moderation record.

Relevant considerations may include:

- Severity of the conduct.
    
- Whether the action is temporary or permanent.
    
- Whether the record is still needed to administer an active restriction.
    
- Whether there is a repeated-offense concern.
    
- Whether an appeal or review remains open.
    
- Whether a legal preservation requirement applies.
    
- Whether the information can be reduced or anonymized while preserving necessary administrative history.
    

A complete moderation history is not automatically justified merely because it may be convenient.

The actual retention schedule must be approved before persistent moderation records are enabled.

## 10. Ban Appeals and Review Records

A dedicated ban appeal workflow is planned and is not confirmed as operational.

Before enabling the Feature, the Operator must define retention rules for:

- Submitted appeals.
    
- Open appeals.
    
- Withdrawn appeals.
    
- Resolved appeals.
    
- Supporting evidence.
    
- Reviewer notes.
    
- Decisions.
    
- Related moderation records.
    

An appeal record may need to remain available while the appeal is being reviewed.

After resolution, the Operator should determine what information remains necessary and delete or reduce information that no longer serves a legitimate purpose.

Appeal records should not be retained indefinitely simply because the original moderation action was permanent.

The retention schedule must be documented before the Feature is treated as operational.

## 11. Technical Logs and Diagnostic Information

Technical logs may be useful for identifying errors, failed operations, and security concerns.

However, logs should not become an uncontrolled secondary database of User information.

### 11.1 Minimize logged information

Where practical, logs should record the information necessary to diagnose an issue without copying entire User submissions or private conversations.

### 11.2 Exclude secrets

Logs must not contain:

- Bot tokens.
    
- Passwords.
    
- API keys.
    
- Authentication codes.
    
- Recovery codes.
    
- Other credentials or authentication secrets.
    

### 11.3 Limit access

Technical logs should be accessible only to individuals who need them for maintenance or security purposes.

### 11.4 Retention period

The Operator must establish a limited, documented log-retention period.

The actual period must reflect the logging configuration and operational needs. This draft does not establish a fixed duration.

## 12. Backups and Recovery Copies

The backup system and lifecycle have not been fully verified.

Before production, the Operator must document:

1. What information is included in backups.
    
2. Whether databases, JSON files, transcripts, attachments, or logs are included.
    
3. Where backups are stored.
    
4. Whether backups are encrypted.
    
5. Who can access backups.
    
6. How often backups are created.
    
7. How long backups are retained.
    
8. How old backups are rotated or deleted.
    
9. How privacy requests are handled when information exists in backups.
    
10. How the Operator verifies that a restored backup does not reintroduce information that should have been deleted.
    

### 12.1 Live deletion and backup deletion

Deleting information from the active database does not necessarily remove it from older backups.

The Operator should use a defined backup-expiration or deletion process so that deleted information does not remain indefinitely in recovery copies.

### 12.2 Restoration

If a backup is restored, the Operator should consider whether it reintroduces records that were previously deleted or corrected.

Where necessary, deletion and correction records should be reapplied after restoration.

### 12.3 No unverified backup promises

This Policy does not claim that backups are currently created, encrypted, rotated, or automatically purged.

Those behaviors must be verified before being represented as operational safeguards.

## 13. Privacy Requests and Deletion

Users may submit privacy requests using the contact method described in the Privacy Policy.

**Contact:** [nextstepstudiosofficial.contact@gmail.com](mailto:nextstepstudiosofficial.contact@gmail.com)

A request may seek access, correction, deletion, or clarification concerning information associated with a User.

### 13.1 Request review

The Operator should:

1. Receive the request.
    
2. Identify the relevant Discord account and records.
    
3. Verify the requester's authority where appropriate.
    
4. Search the relevant storage locations.
    
5. Determine whether the requested action is appropriate.
    
6. Identify any applicable legal or operational retention requirement.
    
7. Carry out the action where appropriate.
    
8. Document the outcome without creating unnecessary additional personal information.
    
9. Respond to the requester.
    

### 13.2 Identity verification

The Operator may request reasonable information to verify the relevant account.

A Discord User ID may help identify the correct records.

The Operator must not request passwords, account tokens, authentication codes, or recovery codes to verify a privacy request.

### 13.3 Deletion limitations

A deletion request may not always result in immediate or complete deletion.

Information may need to be retained where:

- Applicable law requires retention.
    
- A legitimate legal preservation obligation applies.
    
- A record is necessary to resolve a pending matter.
    
- Retention is necessary to protect another person's rights.
    
- The information cannot reasonably be separated from a record that must be preserved.
    

Any exception should be limited to the information and period reasonably necessary for that purpose.

### 13.4 Partial deletion

Where complete deletion is not appropriate or practical, the Operator should consider whether information can be:

- Corrected.
    
- Redacted.
    
- Separated from identifying information.
    
- Restricted from ordinary access.
    
- Retained in a reduced form.
    

### 13.5 Deletion confirmation

The Operator should not claim that information has been deleted until the relevant action has actually been completed.

Where copies exist in separate systems or backups, the response should accurately describe any remaining copies and the process for their removal.

## 14. Discord and Third-Party Records

The Operator can manage only records within systems under the Operator's control or authority.

Deleting a Bot database record does not necessarily delete:

- The original Discord message.
    
- A transcript sent to a Discord channel.
    
- A message stored by Discord.
    
- A copy held by another User.
    
- A record held independently by a third-party provider.
    
- A backup outside the Operator's control.
    

Users may need to contact Discord or another relevant service directly for records controlled by that service.

The Operator should not claim to have deleted information from Discord or another provider unless that deletion has actually been carried out and verified.

## 15. Data Minimization

The Bot should collect and retain only information reasonably necessary for its intended Features.

The Operator should periodically review:

- Whether each stored field is still necessary.
    
- Whether a User ID is sufficient instead of a username and display name.
    
- Whether entire message contents need to be retained.
    
- Whether attachments need to be retained separately.
    
- Whether temporary workflow data can be removed sooner.
    
- Whether old records can be reduced or anonymized.
    
- Whether unused Features are still retaining information.
    
- Whether logs contain unnecessary personal information.
    

New Features should be designed with data minimization in mind rather than collecting information first and deciding later whether it is needed.
